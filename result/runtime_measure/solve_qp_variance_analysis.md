# OSQP Solver solve_qp 시간 편차 분석 보고서

## 1. 분석 목적

MPC(Model Predictive Control) 구현에서 OSQP 솔버의 `solve_qp` 실행 시간이 일정하지 않고 편차가 발생하는 원인을 파악하기 위한 분석.

---

## 2. 데이터 개요

### 2.1 측정 환경
- **솔버**: OSQP (ADMM 기반 QP 솔버)
- **적응형 rho**: 활성화 (50 iteration 마다 체크)
- **MPC horizon**: N = 20
- **샘플링 시간**: Ts (config에서 설정)

| 항목 | 설명 |

## 3. 가설 1: Adaptive Rho Updates가 원인인가?

### 3.1 가설
OSQP의 adaptive rho 메커니즘이 실행 중에 rho 값을 업데이트하면서 추가 계산이 발생하여 solve_qp 시간이 증가할 것이다.

### 3.2 분석 방법
iter_count = 250인 케이스를 대상으로 rho_updates 횟수별 solve_qp 시간 분포 분석.

> **참고**: iter_count가 동일해야 ADMM 반복 횟수가 같아서 공정한 비교가 가능함. iter_count=250이 가장 샘플 수가 많음.

### 3.3 결과: rho_updates별 solve_qp 통계 (iter_count = 250 필터링)

|-------------|---------|-----------|-----------|-----------|---------------|
| 0 | 116 | 2.082 | 1.767 | **5.671** | 0.444 |
| 1 | 195 | 2.075 | 1.758 | 4.073 | 0.355 |

| 4 | 17 | 2.163 | 1.889 | 3.014 | 0.295 |
| 5 | 1 | 2.072 | 2.072 | 2.072 | - |

| rho_updates | 샘플 수 | 평균 (ms) | 최소 (ms) | 최대 (ms) | 표준편차 (ms) | 중앙값 (ms) |

> **두 통계의 차이점**:

> - 전체 데이터: 1,108개 샘플 (다양한 iter_count 포함)
> - 두 경우 모두 rho_updates와 solve_qp 간 유의미한 상관관계 없음

### 3.5 상관관계 분석


### 3.6 결론

**rho_updates는 solve_qp 시간 편차의 원인이 아님**

- 상관계수가 거의 0에 가까움 (0.0028)
- rho_updates = 0일 때와 rho_updates = 1일 때의 평균 시간이 거의 동일 (2.082ms vs 2.075ms)
- 오히려 rho_updates = 0인 경우에 가장 큰 최대값(5.671ms)이 관찰됨

## 6. 순차 실행인데 왜 상관관계가 있는가?

### 6.1 문제 제기
set_env와 solve_qp는 순차적으로 실행되는데(동시 실행 아님), 왜 상관관계가 발생하는가?

### 6.2 MPC 실행 타임라인

```
시간 흐름 →

[느린 MPC 사이클 예시]
├── set_env (153ms) ──────────────────────────────────────┤
                                                           ├── set_qp ──┤
                                                                         ├── solve_qp (2.5ms) ──┤
│←─────────────────────── ~156ms ──────────────────────────────────────────────────────────────→│

[빠른 MPC 사이클 예시]
├── set_env (82ms) ──────────────────────┤
                                          ├── set_qp ──┤
                                                        ├── solve_qp (1.8ms) ──┤
│←──────────────────────── ~85ms ─────────────────────────────────────────────→│
```

### 6.3 핵심 원인: 시스템 부하의 지속성

**시스템 레벨 요인이 ~150ms MPC 사이클 전체에 걸쳐 지속됨**

| 요인 | 설명 | 영향 범위 |
|------|------|-----------|
| CPU 캐시 상태 | L1/L2/L3 캐시의 오염 정도 | 사이클 전체 |
| 메모리 대역폭 | 다른 프로세스와의 경쟁 | 사이클 전체 |
| CPU 주파수 | 터보 부스트/쓰로틀링 상태 | 수백 ms 단위로 변동 |
| OS 스케줄러 | 백그라운드 프로세스 활동 | 수십~수백 ms 지속 |

### 6.4 패턴 분석

```
시스템 부하 높음 (지속 시간 ~150ms)
├── set_env: 느림 (153ms) ← 메모리 집약적 NN 추론
├── solve_qp: 느림 (2.5ms) ← 메모리 집약적 ADMM 반복

시스템 부하 낮음 (지속 시간 ~85ms)
├── set_env: 빠름 (82ms)
├── solve_qp: 빠름 (1.8ms)
```

## 8. 결론

### 8.1 핵심 발견

1. **rho_updates는 원인이 아님** (상관계수 0.0028)
2. **solve_qp 시간은 이중 분포**를 보임 (Mode 1: ~1.9ms, Mode 2: ~3.0ms)
3. **set_env와 solve_qp의 상관관계** (상관계수 0.45)
4. **시스템 부하가 MPC 사이클 전체에 지속**되어 순차 실행 단계들이 함께 영향받음

### 8.2 근본 원인

**알고리즘적 요인이 아닌 시스템 레벨 요인**

```
┌─────────────────────────────────────────────────────────────┐
│                    시스템 레벨 요인                          │
│  ┌───────────────┐  ┌───────────────┐  ┌───────────────┐   │
│  │ 메모리 대역폭  │  │ CPU 캐시 상태  │  │ CPU 주파수    │   │
│  └───────┬───────┘  └───────┬───────┘  └───────┬───────┘   │
│          │                  │                  │            │
│          └──────────────────┼──────────────────┘            │
│                             │                               │
│                             ▼                               │
│  ┌─────────────────────────────────────────────────────┐   │
│  │              MPC 사이클 (~150ms)                     │   │
│  │  ┌─────────────────┐     ┌─────────────────┐        │   │
│  │  │ set_env (NN)    │ ──► │ solve_qp (ADMM) │        │   │
│  │  │ 메모리 집약적    │     │ 메모리 집약적    │        │   │
│  │  └─────────────────┘     └─────────────────┘        │   │
│  └─────────────────────────────────────────────────────┘   │
└─────────────────────────────────────────────────────────────┘
```

### 8.3 개선 방안 (참고)

| 방안 | 설명 | 난이도 |
|------|------|--------|
| CPU 코어 격리 | MPC 프로세스 전용 코어 할당 (`isolcpus`, `taskset`) | 낮음 |
